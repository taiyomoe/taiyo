(branch `rewrite`), in answer to _"What's left to build? What's the best next
step?"_ — then revised the same day against maintainer feedback.

Execute in the order below unless dependencies say otherwise. Each executor:
read the plan fully before starting, honor its STOP conditions, and update your
row when done.

## The one-paragraph picture

The backend and the design system are essentially finished; the product is the
missing middle. `apps/api` ships 74 handlers across 9 routers, every one with a
full OpenAPI spec and integration tests (17 suites). `packages/ui` ships 54
components with 53 Storybook stories. `apps/web` has six routes — a landing
page, two auth forms, three legal pages — **and makes zero API calls**. On top
of that, the API has never been able to tell a client where an image lives:
chapter pages, covers and banners are all returned as bare UUIDs with no
resolvable URL anywhere in the repo. These plans close that gap in the order
that unblocks the most work soonest.

## Why this order

001 first because it is S-effort and it is the difference between "a manga
reading platform" and "a manga platform you cannot read on". The upload
pipeline is complete, tested, and writing pages that nothing can fetch —
`getChapterPageKey` has exactly one importer in the whole monorepo, the writer.

003 in parallel because every frontend feature is blocked on it.

004 because there is currently no query that can power a home page at all: the
only chapter listing is per-media and ordered by chapter number ascending.

### The client decision, and why plan 003 was rewritten

The first draft of plan 003 recommended an OpenAPI-generated client and
rejected Hono RPC. **The maintainer chose RPC and asked for whatever API-side
changes make it work.** Plan 003 now does that, and the rejection reasoning
turned out to be the specification for the fix — both blockers are type-level
and neither touches a handler:

- `ok` and `fail` are _declared_ to return a bare `Response`
  (`apps/api/src/middlewares/context-middleware.ts:12-15`) even though their
  implementations already return `c.json(...)`, i.e. a real `TypedResponse`.
  Only the signature throws the type away. Plan 003 step 1 restores it, using
  `200 | 201` for `ok` (the status is picked from the request method at
  runtime) and a literal per-code status for `fail` (possible because
  `apps/api/src/utils/errors.ts:218` is `as const`).
- The `validate-*` middlewares call `createMiddleware<Env>(…)` and never pass
  the third generic. The installed `hono@4.13.2` signature is
  `createMiddleware<E, P, I extends Input, R>` — `I` is precisely the hook
  `hc` reads request types from, and it is the same mechanism
  `@hono/zod-validator` uses. Plan 003 step 2 fills it in.

Two constraints found while verifying this against
`node_modules/.pnpm/hono@4.13.2/node_modules/hono/dist/types/types.d.ts`, both
handled in the plan: `ValidationTargets.query` is
`Record<string, string | string[]>` (line 542), which coercing Zod schemas
cannot satisfy — so query and path params stay loosely typed on the client
while JSON bodies and all responses are fully typed; and Hono's handler
overloads top out at a path plus 10 handlers, against a heaviest route of 7
middlewares + handler, so there is headroom but not unlimited headroom.

Plan 003 step 6 is a hard checkpoint that verifies inference actually flows
before any UI is built on top of it, and step 7 measures the typecheck cost,
since Hono's own docs warn that RPC inference gets expensive on large apps.

## Recorded, not yet planned

Confirmed findings from this audit that did not become plans. Evidence is
inlined so nobody has to re-audit them.

- **CI has no build gate.** `.github/workflows/ci.yml` runs `knip`, `format`,
  `lint`, `lint:ws`, `test:unit` and `test:integration` (integration against
  real Postgres/Dragonfly/Meilisearch/RustFS — better than most repos), but
  **nothing runs `pnpm build`**. `apps/web/package.json` has a `build` script
  that CI never exercises, and StyleX compile errors are invisible to `oxlint`
  and `tsc` by design (`packages/ui/STYLEX.md` §"Verification"). A broken web
  build can merge undetected. Effort S. This gets sharply more valuable the
  moment plan 005 starts, since 005 is almost entirely StyleX. **Strongest
  candidate for the next plan written.**

- **No deployable artifact exists.** No Dockerfile anywhere in the repo;
  `docker-compose.yml` is infra-only; `apps/worker` has no `build` script so
  `turbo.json` skips it and `start` runs `tsx` on source. `README.md` names
  Coolify + Cloudflare as the deploy target, and there is nothing for it to
  pull. Effort M.

- **Content ratings and flags are returned but never enforced.**
  `packages/db/src/json-types.ts:18-24` defines a per-user `contentRating`
  preference and `packages/config/src/index.ts:25-31` defines its defaults, but
  `grep -rn "settings" apps/api/src` (excluding tests) returns nothing — **no
  handler reads user settings at all**. `POST /medias/search` and every list
  route return all ratings, up to `NSFL`, unconditionally. `showFollowing` and
  `showLibrary` are privacy toggles the API likewise ignores. Effort M. **This
  must close before any public launch**; a client-side blur is not access
  control. Plan 005 states explicitly that it renders whatever it is given.

- **Media search returns no facet counts.** Zero occurrences of `facet` in
  `packages/search/src` or `apps/api/src`; `search-medias.ts:47-59` requests
  only `filter`/`sort`/`page`/`hitsPerPage`. Meanwhile
  `init-medias-index.ts:7-27` already declares 18 filterable attributes.
  Meilisearch returns `facetDistribution` for free when `facets` is passed.
  Effort S, and it is a direct prerequisite for a good browse-filter UI
  (deferred out of plan 005 for exactly this reason).

- **Comments and an in-app reports feature do not exist.**
  `MediaChapterComment` (threaded, soft-deleted, with attachments) was defined
  in `1780040678212_init.ts:735-753` and dropped by
  `1780048678212_refactor-scans.ts:17`. No reports table exists either; the only
  moderation primitive is the admin-initiated `POST /medias/:id/flag`.
  **Plan 008 corrects the privacy policy that currently claims both exist** —
  that is the urgent half. Rebuilding the features is a product decision:
  comments L, reports M. The old column list is a ready-made spec if comments
  return.

- **No notifications substrate.** `packages/queue/src/processor.ts:99-100`
  carries `TODO(plan-001): emit chapter-published notification here once the
notifications producer exists` — the repo's only TODO marker. (Plan 006
  step 7 deletes that marker and folds it into plan 001's maintenance notes, so
  once 006 lands this entry is the only remaining record of it.) No
  notifications table, model or route exists. The events that need one are
  already built: ownership-request approve/reject (which even records a
  rejection reason), upload finished/failed, new follower, new chapter in a
  followed series. Effort M–L; BullMQ is already running for fan-out.

- **README is stale in both directions.** `README.md:5` says "background
  workers are planned but not yet checked in" (`apps/worker` exists and runs in
  `pnpm dev`); its "Not yet in this branch (planned)" list names library,
  history, follows and chapter page upload — all shipped; and the
  project-structure tree omits `apps/worker` and `packages/queue` entirely.
  Effort S. (`apps/web/AGENTS.md` has the same problem and **is** fixed, by
  plan 003 step 10.)

- **Orphaned processed pages on permanently-failed uploads.**
  `packages/queue/src/processor.ts:101-109` marks the task `FAILED` and
  rethrows without deleting the JPEGs it already wrote; `reaper.ts:38-39`
  collects only `stagingKey`s, and the bucket lifecycle rule
  (`packages/s3/src/index.ts:74`) is scoped to `Prefix: "staging/"`. Up to 499
  objects per failed chapter land in a prefix no cleanup path touches. Effort S.

- **`finalize` and `status` upload endpoints are unthrottled.** 7 of 74
  handlers carry `rateLimit`. `create-chapter-upload-session-handler.ts:87` has
  it; `finalize-chapter-upload-handler.ts` — the endpoint that converts an HTTP
  request into CPU-bound `sharp` work in the worker — does not, and neither
  does `get-chapter-upload-status-handler.ts`, which its own OpenAPI
  description tells clients to poll. Effort S.

- **The worker emits no structured logs.** `apps/worker/src/index.ts:13-28`
  uses `console.warn`/`console.debug` with `oxlint-disable` comments; `evlog` is
  a dependency of `apps/api` only, and the worker registers a `ready` listener
  but no `failed` or `error` handler. A failing upload produces zero HyperDX
  signal. Effort S. The repo ships a `review-logging-patterns` skill covering
  exactly this.

- **Health checks are thin.** `apps/api/src/index.ts:65` — `/ping` returns
  `{version}` with no dependency probe; `apps/worker` has no HTTP server at
  all, so an orchestrator can only observe "process alive". Effort S.

- **Titles have create-only CRUD.** `titles` rows can only be created inside
  `POST /medias` (`create-media-handler.ts:302`) and read inside
  `GET /medias/:id`. `PATCH /medias/:id` does not accept titles. A typo in a
  title — which is also the search sort key and document field — is unfixable
  through the API. Covers, banners and staff all have full CRUD; titles are the
  one entity missing it. Effort S, and the pattern exists in four places to
  copy.

- **Five `TASK_TYPES` have no producer or consumer.**
  `packages/db/src/constants.ts:88-96` declares `IMPORT_COVER`,
  `IMPORT_CHAPTER`, `IMPORT_MEDIA`, `CREATE_MEDIA`, `UPLOAD_COVER`,
  `UPLOAD_BANNER`; only `UPLOAD_CHAPTER` exists in code. `packages/db` also
  carries `mangadex-full-api` as a runtime dependency **with zero importers**,
  and `MEDIA_LINK_KEYS` already models `mangaDex`/`anilist`/`myAnimeList`.
  A bulk-import pipeline is strongly implied and would be the cheapest route to
  a populated catalogue, since the `tasks` + BullMQ pattern is already proven.
  Effort S to prune the dead enum values, L to build the importer.
  **Maintainer has seen this and not prioritized it** — left recorded, not
  planned.

- **`userProfiles` is written once and never read.**
  `packages/auth/src/utils/after-user-created-hook.ts:7` inserts a blank row per
  signup; the only other writer is a seed. The table carries banner, birthDate,
  gender, city, country, about and points, and **no route reads or writes it**.
  There is no `GET /users/:id` either — so follows exist with no profile page to
  land on. **Deliberately on hold**: the maintainer intends a larger design here
  and work has not started for that reason. Do not write a plan for this without
  that design.

## Findings considered and rejected

- **`packages/scripts/src/delete-media.ts` queries tables that no longer
  exist.** It issues raw SQL against `"Media"`, `"MediaTitle"`,
  `"MediaChapter"`, `"MediaCover"`, `"MediaBanner"`, `"MediaTracker"`,
  `"UserHistory"` and `"UserLibrary"` (lines 62-78, 118-143), all renamed or
  removed by migrations `1780359259316` and `1780386147385`. **This is
  intentional and not a bug**: the script operates against the _old production_
  database, which still has the old schema; the rewrite is not in production
  yet. Confirmed by the maintainer. Revisit only when the rewrite is promoted
  to prod — at which point the script needs porting, not repairing.

- **"Chapter and group mutations are gated on an ability every user holds."**
  16 routes use `withAuth("read", "OwnershipRequest")`, which
  `apps/api/src/utils/abilities.ts:29` grants to every non-banned user. This
  _looks_ like a missing authorization check and is not: the real gate is the
  `requireChapterAccess` / `requireGroupAccess` / `requireGroupOwnerOrMod`
  middleware that runs immediately after, which is correctly implemented and
  matches the additive ownership model specified in `docs/group-ownership.md`.
  Verified by reading `require-chapter-access-middleware.ts` in full. The only
  real issue is that the CASL subject is used as a "signed in and not banned"
  check under a misleading name — a naming nit, not a vulnerability.

- **Turbo remote caching in CI.** `tooling/github/setup/action.yml:14` installs
  turbo globally but no `TURBO_TOKEN`/`TURBO_TEAM` is configured, and the five
  CI jobs each run a full `pnpm install` plus a paraglide compile. Real waste —
  but the jobs invoke pnpm scripts directly rather than turbo, so this is a CI
  restructure, not a config toggle. Low leverage until a build job exists worth
  caching. Revisit alongside the CI build gate above.

- **Additional Meilisearch indexes** (staffs, groups, users).
  `packages/search/src/client.ts:10-12` makes adding one cheap, and all three
  have full routers. Premature: there is no UI that would consume them, and
  plan 005 does not need them. Revisit once browse and search surfaces exist.

- **User ratings and reviews.** Part of the original "nothing is ranked by
  popularity" finding, deliberately **not** included in plan 007. A rating
  system requires product decisions the advisor should not make unilaterally:
  the scale, whether averages show before a vote threshold, whether review text
  exists, and how to resist brigading. Plan 007 ships library-count popularity
  instead, which needs none of those decisions, and documents itself as the
  template if ratings follow.

- _Keeping the "why" comments and deleting only the restatements (the literal
  99/1 rule)_: rejected by the owner in favour of a full purge plus the doc
  harvest. Applied literally it would have removed only ~40% of the comments
  here, because this repo's comment population is unusually rationale-heavy.

- _Purging YAML, `.env.example` and `docker-compose.yml` comments_: not code,
  and in those files the `#` lines are the only documentation each key has.

- _Adding a lint rule to enforce comment-freedom_: `oxlint` ships no such rule
  today. The detector script in plan 006 plus the policy added to `README.md`
  are the stand-in.

- **A `PasswordInput` Storybook story.** It is the only one of the 54
  `packages/ui` components without a `.stories.tsx` / `.docs.mdx` pair. Real,
  but S-effort cosmetic completeness with no downstream unblock. Worth doing in
  a spare five minutes, not worth a plan file.

- **Renovate being disabled** (`.github/renovate.json:3`) and the
  `NEXT_PUBLIC_` `clientPrefix` left in `packages/s3/src/env.ts`. The first is
  a deliberate, documented decision for the duration of the rewrite
  (`README.md` §"Package management"); the second is inert scaffold residue
  behind a `clientPrefix` with an empty `client: {}`. Neither is a finding.

## What this audit did not cover

- `apps/storybook` internals beyond story coverage counts.
- `packages/auth`'s Better Auth plugin configuration and lifecycle hooks in
  depth — only its client surface and the `after-user-created-hook`.
- The 17 integration-test suites were inventoried, not read. Test _quality_ was
  not assessed; only presence and structure.
- Performance: no query plans were examined and no load testing was done. The
  index observations above come from reading migrations, not from `EXPLAIN`.
- Security received a targeted pass (auth gating, rate limiting, content-rating
  enforcement, the ability-naming question) rather than a full review. The
  repo ships a `/security-review` command for that.
